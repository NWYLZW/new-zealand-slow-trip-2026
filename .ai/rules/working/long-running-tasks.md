# 长任务、断点恢复与进度管理

在批量调研、跨多轮开发、用户反复说“继续”或工作可能被压缩/中断时阅读本页。

## 建立三本账

长任务不能只靠聊天上下文。维护以下可恢复状态：

1. **范围账**：完整目标、非目标、硬约束、授权和完成定义。
2. **对象账**：每个地区/事件/酒店/文件的状态、证据、缺口和下一动作。
3. **验证账**：哪些检查已在哪个状态下通过，后续哪些改动使旧结果失效。

优先把可执行状态放进数据字段、审计脚本或报告，而不是只写一篇会过期的进度说明。

## 原子推进

- 将工作切成能独立验证的批次：一个地区、一类状态、一个组件族或一个数据迁移步骤。
- 每批遵循“检查基线 → 修改 → 局部验证 → 更新对象账”。
- 不在尚未验证的批次上继续堆第二层大改，避免错误范围指数扩散。
- 长命令使用可恢复的会话并定期取回输出；不要连续发送“继续”却没有真正执行工具。

## 断点与交接

每个自然断点至少记录：

- 当前完整目标和不可违反的约束；
- 已完成、已验证、仅实现未验证、未开始、被阻塞的项目；
- 当前 Git/服务/浏览器状态；
- 精确的下一步及其输入；
- 已知警告、失败尝试和不要重复的路径；
- 哪些结论来自实时证据，哪些需要重新刷新。

交接摘要应让接手者能继续，而不是重新调研；但临时 PID、过期 tab 句柄和未经证实根因不能沉淀成长期规则。

## 进度状态要可区分

不要只用“待处理/完成”。至少区分：

- 未开始；
- 研究中；
- 已查但证据不足；
- 数据已写入未验证；
- 局部验证通过；
- 全量验收通过；
- 外部阻塞；
- 明确排除/不适用。

状态必须能回答“接下来做什么”，并尽量由报告脚本自动计算，减少人工计数漂移。

## 进度汇报

面向用户先说结果和真实剩余：

- 用分母和分类，例如“26/26 事件通过；仍有跨事件复用警告”；
- 区分“没开始”“查了没取到”“有旧数据待刷新”“明确不可用”；
- 只报告本轮新增证据，不把早已完成的内容反复包装成进展；
- 工具失败与产品失败分开报告；
- 不用“马上”“最后一步”反复承诺，除非确实只剩可验证的一步。

## 优先级

通常按以下顺序：

1. 会造成错误决策、隐私泄露或数据损坏的问题；
2. 用户当前明确阻塞点；
3. 尚未开始但影响全量完成的硬缺口；
4. 已查但不可复现/旧数据刷新；
5. 视觉润色和非阻断警告。

不要为了让指标好看优先做最容易的对象；应优先降低未知和错误风险。

## 收尾

- 重新从目标推导完成要求，不从“已经做了什么”反推目标。
- 运行全量门禁，确认旧验证未因后续改动失效。
- 删除一次性脚本、下载残片和死数据；保留真正可复用的报告/审计。
- 把反复出现且稳定的经验送入 [`../knowledge/maintenance.md`](../knowledge/maintenance.md)，一次性过程留在 Git 历史或任务记录。
