# 需求建模与授权边界

在新需求、模糊反馈、截图批注、范围变化或准备大改前阅读本页。

## 把原话转成可执行契约

先整理六项，不急着写代码：

1. **目标**：用户最终要获得什么能力或决策结果。
2. **非目标**：这轮明确不做什么，避免顺手扩大范围。
3. **硬约束**：技术栈、工具、隐私、证据、时间和操作禁区。
4. **成功示例**：用户给出的截图、页面、现有组件或一条代表数据。
5. **影响面**：代码、数据、中英、URL、状态、部署和文档的消费者。
6. **验收证据**：哪些文件、命令、页面行为或数据报告能证明完成。

用户说的是表面方案时，先识别底层意图。例如“弄成日历”通常意味着要看清整段时间关系，不只是换一个日历皮肤；“地图上标点”意味着空间顺序、路线类型和可操作性都要成立。

## 事实、偏好和授权分开

- **事实**：日期、订单、已有代码状态，可由证据核验。
- **偏好**：少文案、纯色、单大床、松弛节奏，会影响方案评分。
- **授权**：是否允许登录、提交表单、预订、commit、push、创建外部资源。授权不能从偏好或“继续”中推断。
- **环境状态**：已登录 IAB、脏工作区、服务端口，只是当前条件，不是永久规则。

每轮新信息先判断属于哪一类。订单截图可以更新事实，但不自动授权支付；“push”授权当前合法改动的提交推送，不授权 force、清理工作区或发布其他仓库。

## 何时自主推进，何时询问

可以自主推进：

- 只读检查和可逆诊断；
- 范围内的常规实现选择；
- 能从仓库、真实来源或当前页面确定的答案；
- 不改变用户决策的细节。

必须停下询问：

- 两个选项会产生明显不同的产品结果，而证据无法确定偏好；
- 需要提交外部表单、付款、预订、公开仓库、删除数据或扩大权限；
- 用户要求的入口/日期/对象不能唯一定位；
- 用户已要求先看样例或确认方案，当前尚未确认。

问题只问最小阻塞信息；不要在尚未调研前一次性抛出一串泛化问题。

## 用垂直样例校准

面对批量页面或数据，先选一个有代表性的完整样例，端到端打通：

- 真实来源与证据；
- schema 和状态表达；
- UI、图片和交互；
- 本地持久化/共享边界；
- 自动审计与浏览器验收。

样例是用来暴露遗漏，不是降低最终范围。用户确认样例后再抽象公共原语并批量扩展；用户要求全量后不要把“样例完成”冒充整个目标完成。

## 处理范围变化

- 最新明确决定覆盖旧假设，但要追踪所有下游影响。
- 用户纠正“不是记录”“不住酒店”等话语时，立即停止相反动作并清理已引入的错误状态。
- 新需求若只是补充，保持原目标；若明确替换，停止旧路径，不继续做沉没成本工作。
- 需求变化后重算验收矩阵、优先级和数据查询条件，不沿用旧日期/旧候选/旧页面结果。

## 完成标准

- 每条显式要求和关键隐含意图都有实现/证据对应。
- 没有把未经授权的外部操作当正常实现步骤。
- 样例、部分完成和全量完成被准确区分。
- 范围变化已传播到所有消费者和验收项。
