# 行程、交通与活动数据

在更新日期、路线、航班、租车、住宿段、活动或用户订单截图时阅读本页。

## 事实优先级

从高到低使用：

1. 用户最新明确决定与其提供的有效订单/电子票证据；
2. 航司、租车行、活动方、酒店的确认页或邮件；
3. 官方时刻/政策页面；
4. 已核验预订平台；
5. 行程建议和社交经验。

新证据推翻旧计划时，保留必要的状态说明，不让旧假设继续出现在其他页面。

## 更新前建立影响矩阵

至少检查这些消费者：

- `src/tripData.js`：日期、事件、住宿、航班、租车、预订项；
- `src/components/RouteMap.jsx`：点位、路线段、月历事件、详情；
- `src/routeI18n.js`、`src/englishTripData.js` 和 `*En` 字段；
- `src/components/panels/RentalCarPanel.jsx`、活动/住宿面板；
- `src/data/regionalHotels.js` 等住宿入住日期；
- `src/eventMedia.js`、`src/eventLinks.js` 与社交攻略键；
- README 或公开说明中是否复制了相关事实。

不要只改一个可见标题。日期改变通常会级联影响住宿夜数、价格查询区间、取还车余量、路线、日历和预订进度。

## 订单与票面解读

- 区分“已付款”“出票中”“已出票/状态 OK”“已确认”，只写证据能够证明的状态。
- 明确票面是单人还是双人；单人金额不能乘二后声称是订单总额，另一位未见票面就标待核对。
- 记录本项目需要的航班号、日期、机场、时刻、航站楼（若有）、舱位、行李/餐食（若明确）和状态。
- PNR、电子票号、确认号、姓名、证件信息只保留在用户私有渠道，不进入仓库。
- 跨日和时区用当地日期时间表达，并明确“次日”；不要用服务器时区做旅程逻辑。

## 可行性分析

- 先锁定硬约束：落地/起飞、取还车、已订活动、入住/退房、必须到场时间。
- 再计算缓冲：入境和取行李、国内/国际航站楼、加油、还车、停车、恶劣天气、道路/渡轮/活动报到。
- 给出“可行 / 偏紧 / 不可行或需备选”的结论及原因，不只抄时间表。
- 松弛旅行默认每天一个主重点，连续住宿优先，避免无收益的早起和换酒店；高强度项目标成备选并说明代价。
- 推荐应结合两人行程、行李、自驾、停车、活动时段和第二天动线，而非泛化景点榜单。

## 主方案、备选与确认状态

- 主方案是当前默认执行路径；备选必须标触发条件（天气、库存、体力、道路等）。
- 已确认订单不因更便宜的旧建议被静默覆盖；需要改变时先指出取消/沉没成本和影响。
- 用户删除住宿或改变航班后，清理所有旧住宿描述、统计、地图点位和预订清单，避免“9月29日不住”但总览仍显示入住。

## 数据写法

- 使用稳定 ID、ISO 日期和明确本地时间；显示层再转换中文日期。
- 中英文同步；专名保留官方英文/毛利语，中文是辅助而非替代。
- 价格、政策和状态附核验日期与来源；建议与事实分字段或分段表达。
- 事件标题一旦作为媒体/社交攻略键使用，改名必须同步关联数据和审计预期。

## 完成标准

- 时间线没有冲突，航班—取还车—住宿—活动之间有现实缓冲。
- 总览、南北岛、租车、住宿、活动、中英和地图一致。
- 隐私字段未落盘。
- 事件媒体、构建和受影响页面的深链接/移动端已验证。
