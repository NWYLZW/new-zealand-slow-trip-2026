# 界面与交互设计标准

在调整布局、视觉层级、地图、日历、详情、筛选或响应式行为时阅读本页。

## 产品语气

- 这是旅行决策界面，不是宣传海报。优先显示日期、地点、交通、已确认状态、价格/条件和下一步动作。
- 删除无信息量的口号、英文 kicker、重复标题和“解释 UI 的说明文案”。有帮助的信息应靠结构、标签和状态表达。
- 避免超大 hero、无边界留白、重复外层 Card、独立路线图例和为了装饰而存在的内容块。
- 文案要具体：用“10月8日 11:00 基督城机场还车”而非“轻松返程”；用“已查目标日期 · 无可复现价格”而非含糊的“待更新”。

## 视觉语言

- 使用克制的旅行杂志感：真实目的地图片、纯色地区编码、清晰排版和轻量毛玻璃。
- 不新增渐变；状态、地区、路线和背景使用稳定纯色。触及仍有历史渐变的区域时，在不损害可读性的前提下改为纯色或透明叠层。
- 布局容器少圆角或小圆角；按钮、Chip、图片和内部控件可保留适度圆角。不要让每层嵌套都成为圆角卡片。
- 毛玻璃必须保证文字对比度，且在低性能/打印/小屏场景允许退化。
- 使用同一套 spacing、radius 和颜色 token；不要在新组件里散落近似常量。

## 信息架构

- 行程总览用“地图 + 月历”表达空间和时间；日历格内只放能快速判断当天的核心信息，详情通过点击展开。
- 同地区/同住宿连续日期使用一致颜色和连续视觉，避免用户把同一住宿误解成多次搬家。
- 页面标题、面包屑和详情返回形成层级；移动端可截断中间层，但必须保留当前项和明确返回路径。
- 搜索、筛选和地图在住宿页协同：编号用于地图定位，酒店内容进入详情，列表可独立滚动，地图在桌面保持上下文。
- 状态必须能区分已确认、推荐、备选、待核价、不可复现、明确无房和不可选择，不能只靠灰色或一个“待定”。

## 地图

- 地图必须有真实点位和路线；点位编号/标签、路线顺序、陆路/飞行/游船样式要可辨认。
- 缩放应请求或呈现对应精度，路线、箭头和点位随地图投影变化；不要只用 CSS 放大静态图。
- 自驾优先真实道路；无 key 时允许 Leaflet/OSM 或明确的退化方案，并保留“在 Google 地图打开”入口。
- 航线可用虚线或曲线；路线越晚可以更深，但不要再额外放一张重复图例卡。
- 地图交互按钮要可访问、有 `aria-label`，移动端不得遮挡内容。

## 日历与详情

- 使用真实月历七列网格，保持星期和日期对齐；不能用一列卡片冒充日历。
- 点击日期负责选择行程区域或当天；点击事件负责打开事件详情，两种动作不要混淆。
- 详情使用可分享 URL。事件、酒店、活动和图库的打开、tab、关闭、浏览器前进/后退都应恢复一致状态。
- 详情图使用真实本地图，头图、房型图、公共区域图明确区分；全屏图库保留来源和缩略图导航。
- 移动端详情可全屏；标题单行或有控制的截断，关闭/返回按钮始终可见，内部 Card 不得被全屏选择器误伤。

## 响应式与无障碍

- 至少验证桌面、平板和约 436px 手机宽度；无横向滚动，七列日历必要时隐藏次要文案而非破坏列宽。
- 可点击的非原生元素应改为 Button/ButtonBase 或提供键盘、焦点和 ARIA 行为。
- 不仅靠颜色传达状态；配合文字、图标或边框。
- 图片有准确 alt；外链标识、新窗口行为和加载失败状态清楚。

## 验收问题

1. 用户能否在几秒内回答“哪天、去哪、住哪、是否确认、还要做什么”？
2. 是否存在重复标题、重复卡片或只为解释 UI 而存在的文案？
3. 地图/日历/详情是否在缩放、刷新、返回和手机尺寸下仍一致？
4. 状态和证据是否具体，还是视觉上掩盖了未知？
