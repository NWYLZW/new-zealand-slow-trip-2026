# 住宿调研与报价数据

在新增/核验酒店、民宿、公寓、B&B、房型、价格、库存、评分或图片时阅读本页，并先遵守 [`evidence.md`](evidence.md)。

## 查询口径

- 从 `regionalStays`/当前行程读取入住和退房，不从历史对话抄日期。
- 默认是 2 位成人、1 间房；若用户修改则同步平台 URL 生成和审计。
- 比较整段住宿总价。多晚可额外显示每晚均价，但不能反过来把每晚价当总价。
- 只比较用户接受的真实床型/房型；若当前偏好是一张大床/特大床，不混入双床或两张双人床来制造低价。
- 平台会员价注明登录/会员等级；公开价与会员价分开。

## 候选质量

- 每个当前地区至少保留 10 个可见研究选项，并至少有可选 `hotel` 和 `home`；具体契约以 `audit-accommodation-data.mjs` 为准。
- `home` 只用于真实整套公寓/度假屋/主人经营 B&B 等，不把 Motel 或普通酒店重标为民宿。
- 不为数量加入身份不清、位置不合、评价证据弱或不适合行程的候选。
- 每家写明行程相关理由：到活动/机场/市中心距离、停车、自驾动线、连续住宿、入住时间和真实缺点。
- 地理边界外候选必须明确实际距离和代价，不能用区域名掩盖偏远位置。

## 每家住宿的数据契约

至少核验并双语记录：

- 稳定 ID、官方英文名、类型、坐标、地图查询；
- 推荐理由、摘要、交通、停车、至少 2 个优势和 2 个注意点；
- 至少 2 个与行程相关的附近地点；
- 至少一个具体推荐房型：平台原名、`rateKey`、床型、面积/设施（来源有才写）；
- 数字评分、满分和评价数，并标来源；编辑标签不是住客评分；
- 官方/平台具体房源 URL；
- 当前入住段的报价或可用性快照、核验日和明确状态；
- 至少 5 张本地、唯一、可追溯的当前住宿图片。

字段细节以 `scripts/audit-accommodation-data.mjs` 为可执行契约；规则与审计冲突时先确认代码现状，再同步修正规则或审计，不能绕过。

## 价格与政策

- 记录平台、房型、总价 NZD、查询条件、核验日；人民币仅作约值并注明汇率/日期。
- 分开记录不可退、可免费取消、取消截止、扣款/预付、早餐、停车、税费和剩余房数。来源没明确的字段写未知。
- 不同平台房名可归到同一实际房型，但保留各平台原名和对应证据。
- `exact-rate-verified` 必须有可复现总价；动态报价仍提示付款前刷新。
- 有旧目标日期数字但已过时，展示“历史报价 + 核验日 + 待刷新”，不要看起来像完全没查。
- 已检查但被动态加载、风控或跳转阻断，写“已查目标日期 · 无可复现价格”；未开始结算才写“目标日期待查询”。
- 只有官方或可靠平台明确返回精确日期无库存才能用 `exact-date-unavailable`；请求失败、404 旧入口、验证码或空页面不算售罄。

## 图片

- 房型图来自该房型详情图库；酒店总图库只能标公共区域/外观，不得冒充房型。
- 每张图本地化，记录具体 property/listing 页面 URL、`propertyId`、`reviewedAt`、中英标签和来源。
- 不使用搜索结果缩略图、浏览器整窗截图、占位图、同品牌其他门店或景点图。
- 同一张图的裁剪/压缩/改编码仍是重复图；SHA 去重后还需感知哈希和人工核对。
- 图库至少覆盖对选择有用的维度：卧室、浴室、厨房/客厅（若有）、外观/公共空间；不是随便凑 5 张。

## 工作顺序

1. 运行 `npm run report:accommodation-recheck`，按状态而不是列表顺序排优先级。
2. 优先补“目标日期待查询”，再刷新旧报价，再处理已查但不可复现。
3. 自动脚本只用于其真实覆盖的平台；其余用登录态浏览器逐家核验。
4. 在数据对象中保留来源、条件和失败原因，避免下一轮重复调查。
5. 更新 UI 状态文案，让用户能区分“没查”“查不到”“旧价”“无房”。
6. 运行住宿审计、视觉重复审计、构建和目标地区浏览器验收。

## 推荐与选择

- “首选”表示最适合这趟行程，不等于最低价。比较位置、房型、停车、取消、连续库存、活动动线和成本。
- 推荐中写明强项、妥协和适用条件；异常高价或只剩不合偏好的房型可以保留证据但设为不可选。
- 用户已选住宿与研究候选分开；不可因数据刷新静默覆盖用户选择。
