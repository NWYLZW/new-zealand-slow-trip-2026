# 数据管线、Schema 与迁移

在新增来源、批量录入、调整数据结构、拆分大文件、生成派生字段或强化审计时阅读本页。

## 分清数据层

- **来源事实**：页面/订单/官方接口实际给出的原始字段和来源上下文。
- **规范化数据**：统一 ID、日期、币种、房型键、状态和双语字段。
- **派生数据**：夜数、人民币约值、进度、推荐排序、地图路线等可计算结果。
- **展示文案**：面向用户的摘要、标签和建议。

来源事实与建议不能混在同一字段；可计算值尽量在一个地方派生，避免多个文件手工复制后漂移。

## Schema 演进

1. 先列出现有消费者、审计、URL/localStorage 和持久化 JSON。
2. 用一个垂直样例验证新字段能表达真实状态。
3. 新 schema 应区分未知、未查、查无可复现结果、旧数据、确认值和不适用；不要用 `null` 承载所有含义。
4. 保持稳定 ID 和兼容聚合 export；必要时写显式迁移/适配，而不是悄悄改键。
5. 同步中英字段、生成器、报告、审计和 UI 回退。
6. 迁移完成后搜索旧字段/旧状态并删除临时代码。

## 来源与派生

- 每个动态事实带 `sourceUrl`、核验时间、查询条件和状态；图片还带对象 ID 和语义标签。
- 派生数字说明输入和算法：夜数来自 ISO 日期，人民币约值来自带日期汇率，进度来自当前集合而非硬编码。
- 覆盖/补丁文件适合集中修正可追溯事实，但要避免形成多层互相覆盖而不知道最终值；聚合顺序必须明确。
- 归档数据与当前选择分开，默认不进入当前报告、地图和审计分母。

## 批量导入

- 先验证来源页面和许可证/使用边界，再下载或转换。
- 用确定性脚本做机械转换，用 `apply_patch`/人工审查做语义修改。
- 批次必须可重复运行或显式一次性；一次性脚本完成后删除，长期报告脚本保留并写入 package scripts。
- 每批检查重复 ID、重复入口、错误对象图片、未来日期、非当前入住段和秘密。
- 不让自动补全文案把中文复制到英文字段、把占位值变成看似完整的数据。

## 审计是可执行契约

- 当真实质量标准反复被违反时，把它变成审计：数量/类型、来源、日期条件、双语、唯一性、状态互斥、图片语义等。
- 审计必须检查当前实际消费者，不只扫描字符串；同时确认归档/不可选对象的特殊规则。
- 哈希、正则和计数是候选生成器，不是语义真相；图片归属、房型匹配和推荐合理性仍需人工抽查。
- 报告脚本展示待办和状态分布，审计脚本负责硬失败；不要混淆二者。

## 大文件拆分

- 按稳定业务边界拆分（地区、领域、媒体类型），保留薄聚合入口。
- 拆分前后对比 export、对象数量、ID 集和关键报告，确保没有静默丢失。
- 避免循环依赖和跨文件修改同一对象；共享 helper 放独立模块。
- 拆分只是可维护性手段，不应改变数据语义或用户选择。

## 完成标准

- 来源、规范化、派生和展示边界清楚。
- 新状态能表达真实未知，不需要误导性占位。
- 迁移前后对象/exports/选择保持一致或有明确变更说明。
- 报告、审计、构建和代表性 UI 同时验证。
