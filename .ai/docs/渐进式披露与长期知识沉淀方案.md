# 渐进式披露与长期知识沉淀方案

状态：第一阶段已落地
最近评审：2026-08-03

## 1. 目标

让接手者用尽量少的读取成本获得当前任务所需的完整约束，同时让高价值经验从对话和个人记忆迁移为可发现、可执行、可验证、可淘汰的仓库资产。

本方案解决两个不同问题：

- **渐进式披露**：当前任务应该先读什么、按什么顺序读、何时停止继续加载；
- **长期沉淀**：什么经验值得进入仓库、放在哪一层、何时升级为自动化、怎样避免陈旧和重复。

## 2. 当前评估

仓库已经具备较好的第一层基础：根 `AGENTS.md` 保持短小，专项规则按 `working/`、`developing/`、`design/`、`research/` 等稳定职责拆分，自动审计能检查入口长度、链接、npm 命令和临时信息污染。

继续扩展时会出现三个瓶颈：

1. 专项规则索引按“知识分类”组织，实际任务往往要手工组合需求、领域、验证和交付规则；新接手者知道单篇规则，却未必知道完整阅读顺序。
2. 规则虽然结构相似，但缺少统一、可机器读取的触发、产出和验证契约，自动审计只能检查“文件存在”，不能检查“是否可路由、可完成”。
3. 历史经验容易只增不减。没有成熟度、复审和退役机制时，规则数量会增长，重复和过期内容会逐渐抵消渐进式披露的收益。

## 3. 目标信息架构

```text
AGENTS.md                         所有任务必读：高风险约束、场景入口、最小门禁
.ai/rules/README.md               路由中枢：常见场景 + 专项兜底
.ai/rules/scenarios/              场景阅读包：顺序、产出、停止点、完成门槛
.ai/rules/{domain}/               权威规则：稳定工作法、证据模型、验证契约
.ai/docs/                         架构、路线图、设计决策，不是任务默认上下文
src/、scripts/、数据与报告        当前事实、可执行契约、实时状态
任务记录/进度账本                 暂态过程，可恢复但不自动成为长期规则
```

核心原则是“两轴路由”：

- 场景轴回答“这类任务完整地怎么走”，面向高频端到端工作；
- 专项轴回答“这个领域具体遵守什么”，面向稳定的单一职责。

场景不复制专项正文，只链接权威规则。专项规则也不反向堆叠整套场景，避免形成循环必读。

## 4. 场景阅读包设计

第一阶段提供六个高频入口：

| 场景 | 核心路径 | 解决的问题 |
| --- | --- | --- |
| 功能、代码与数据变更 | 需求 → 一条领域规则 → 验证 | 避免遗漏影响面和消费者 |
| 住宿调研与核价 | 证据 → 住宿 → 按需浏览器 → 验证 | 统一查询条件、状态和图片语义 |
| UI 反馈闭环 | 反馈 → 界面 → 按需架构 → 验证 | 从局部批注收敛到一致性修复 |
| 长任务与批量工作 | 需求 → 长任务 → 按需协调/数据 → 验证 | 支持断点恢复和真实进度 |
| 故障诊断与恢复 | 诊断 → 按需工具/领域 → 验证 | 限制机械重试和高风险恢复 |
| 提交、推送与发布 | 授权 → 验证 → 隐私/Git | 防止把实现完成误当成交付完成 |

每个场景文件只保留五类信息：

1. 触发条件；
2. 有序阅读路径及按需分支；
3. 预期产出；
4. 停止/用户确认条件；
5. 完成门槛。

新增场景需要同时满足：高频出现、通常组合至少两条规则、顺序或停止点会影响正确性。仅仅多一个领域名，不足以创建新场景；应继续使用专项索引。

## 5. 元数据契约

专项规则使用轻量 frontmatter：

```yaml
---
kind: rule
id: research.evidence
scope: research
triggers: [evaluate-source, write-research-conclusion]
outputs: [traceable-evidence-record, confidence-aware-conclusion]
verification: [source-query-and-date-are-recorded, unknown-is-not-presented-as-fact]
last_reviewed: 2026-08-03
---
```

场景将 `scope` / `verification` 替换为：

```yaml
reading_order: [../research/evidence.md, ../verification/quality-gates.md]
stop_conditions: [query-conditions-are-incomplete]
completion_gate: [evidence-status-is-explicit, affected-audits-pass]
```

约束：

- `id` 全仓唯一且稳定；移动文件时优先保持 id，语义职责改变时才新建 id；
- 数组值使用短标识，正文负责解释，不在 frontmatter 塞长段自然语言；
- `reading_order` 只列必读核心路径，条件分支留在正文；
- `last_reviewed` 表示内容与当前仓库契约核对过，不等于文件最后编辑时间；
- 元数据服务路由和审计，不替代正文中的取舍、例外与示例。

## 6. 文档边界

| 信息 | 权威位置 | 不应放入 |
| --- | --- | --- |
| 所有任务必须知道的高风险约束 | `AGENTS.md` | 多步骤领域教程 |
| 高频端到端路径 | `scenarios/` | 规则正文副本 |
| 稳定、可复用的工作法 | 专项规则 | 一次性事故时间线 |
| 架构决策与演进计划 | `.ai/docs/` | 每次执行必读入口 |
| 行程、价格、数量、当前完成状态 | 源码、数据、审计、报告 | 长期规则 |
| 跨轮任务的恢复状态 | 任务账本或结构化数据 | `AGENTS.md` |
| 可机械判断的正确性标准 | 审计、测试、schema | 仅靠文字提醒 |

同一约束只有一个权威正文。其他文件使用链接和一句用途说明，不复制段落。事实变化时修改事实源；工作方法变化时修改规则；信息架构变化时修改本方案。

## 7. 知识生命周期

经验按四级成熟度流动：

1. **观察**：单次现象或未证实假设，留在任务记录，不进入规则。
2. **模式**：重复出现且能指导下一步，合并进已有专项规则，必要时更新经验映射。
3. **契约**：影响正确性、隐私或大规模返工，且能定义明确门槛；写入规则并增加审计/测试。
4. **基础设施**：高频、机械、稳定的契约；升级为脚本、schema、报告、组件或生成器，规则只解释使用边界。

提炼时回答：触发场景、失败模式、通用原则、执行动作、验证证据、边界/例外。缺少验证证据的“经验”暂不升级为契约。

建议记录“被拒绝沉淀”的理由，而不是保存全部过程：例如一次性环境故障、动态报价、临时进程信息、不可复现推测。这能避免后来者再次把偶然现象制度化。

## 8. 复审、合并与退役

知识治理的重点不是持续增加文件，而是保持有效密度。

- **随改复审**：代码路径、schema、审计命令、部署方式改变时，同一提交更新引用它们的规则。
- **到期提示**：规则超过 180 天未评审时审计给出提示；提示要求核对，不要求无意义地刷新日期。
- **季度抽查**：选取真实任务回放场景路由，检查是否少读、漏读或产生冲突；优先修入口和自动化，不为覆盖率堆新文档。
- **年度清理或重大重构后清理**：合并重复规则、删除已被代码/审计完全替代的操作细节、为失效场景做退役记录。
- **退役标准**：触发条件不再存在、已有更权威规则、行为已由基础设施强制且无需额外判断，或长期回放没有消费者。

合并或退役时更新所有路由和链接；不要保留两个都像权威版本的文件。Git 历史承担追溯，当前规则只表达当前契约。

## 9. 自动审计策略

`npm run audit:ai-rules` 应逐步覆盖：

- 根入口长度预算；
- 所有规则/场景有完整 frontmatter、唯一 id 和合法评审日期；
- `scope` 与目录一致；
- 所有场景 `reading_order` 指向存在的专项规则；
- 根入口和索引可发现所有场景，索引可发现所有专项规则；
- 文档链接和 npm script 存在；
- 单篇规则长度预算，防止重新长成总手册；
- 对话 id、临时路径、socket、PID 等暂态信息不进入长期文档；
- 评审超期只告警，结构、断链和契约缺失才阻断。

下一阶段可增加但不应立刻阻断开发的能力：

- 校验规则正文中反引号路径是否真实存在，并提供显式动态路径豁免；
- 检测场景触发词高度重叠，提示合并或写清优先级；
- 记录代表任务实际加载的文档数、回退到专项索引的比例和首轮验收通过率；
- 用任务回放验证“从入口能否找到正确规则”，而不只验证 Markdown 结构。

## 10. 分阶段落地

### 第一阶段：结构化入口（已完成）

- 根路由从二十余条专项链接收敛为六个场景入口和一个专项兜底；
- 新增场景阅读包，不复制规则正文；
- 所有专项规则和场景增加轻量元数据；
- 审计覆盖元数据、唯一 id、场景路径、长度和评审日期。

### 第二阶段：可观测性

- 在真实任务中记录“命中场景、追加规则、是否回退、遗漏原因”；
- 连续观察一段任务样本后再调整场景，不凭文档作者直觉增加入口；
- 为高频人工核对补审计或报告，把契约从文档升级为执行能力。

### 第三阶段：半自动维护

- 生成规则目录、依赖图和超期报告，减少手工维护索引；
- 对规则变更运行代表任务回放；
- 对退役、合并和迁移提供显式重定向检查，避免隐性断路。

## 11. 验收标准

本轮结构优化满足：

- `AGENTS.md` 不超过 80 行，常见任务不需要从二十余条规则中手工拼装路径；
- 每个常见场景在一页内说清阅读顺序、产出、停止点和完成门槛；
- 场景与专项规则没有正文复制，专项规则仍有唯一权威位置；
- 每个规则/场景均可被机器识别，所有路径、链接和 npm 命令通过审计；
- 动态项目事实、敏感信息和历史会话内容未进入长期文档；
- `npm run audit:ai-rules`、`npm run build`、`git diff --check` 通过。

长期有效性的判断指标：常见任务首轮能命中正确场景；平均只加载一个场景和少量专项规则；因漏读规则造成的返工下降；规则重复/断链为零；高频人工标准持续升级为自动化，而非持续增加文字。

## 12. 风险与取舍

- **多一层路由**：场景层增加一次跳转，但换来稳定顺序和停止点。通过保持场景短小、只服务高频组合控制成本。
- **元数据与正文漂移**：元数据可能更新而正文未更新。审计只能发现结构问题，真实任务回放和随改复审仍不可省略。
- **场景过多**：入口数量增长会重新制造选择困难。坚持高频、跨规则、顺序敏感三个准入条件，低频任务留在专项索引。
- **日期形式化**：机械刷新 `last_reviewed` 会制造虚假新鲜。超期只提示，并要求以路径、命令、行为或回放证据完成复审。
- **过度自动化**：不是所有判断都适合脚本。来源可信度、视觉适配和推荐取舍保留人工判断，脚本负责可重复的结构和一致性检查。

## 13. 长期维护建议

1. 把“减少下一次判断成本”作为沉淀标准，而不是把“记录了多少”作为成果。
2. 每次新增规则前先搜索现有权威位置；能补充就不新建，能自动化就不长期保留手工清单。
3. 对隐私、数据一致性、动态事实状态和发布安全等高代价问题，优先从文字升级到测试/审计。
4. 用代表性任务回放检验路由质量：是否命中、是否少读、是否在正确确认点停下、是否能证明完成。
5. 把动态事实和任务进度留在可查询的数据/报告里；规则只保留稳定方法和状态语义。
6. 为删除知识建立正反馈：能证明规则已被合并、替代或失效，和新增规则同样是有效沉淀。
